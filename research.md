# research.md - State of the Art: ML Recipe Prediction & Inverse Formulation Design

**Project:** Predict physical/textural/rheological properties of a plant-based cheese
from formulation + process, and solve the *inverse* problem - given target
properties, output the optimised recipe.
**Data regime:** ~600 usable recipes (formulation + measured properties), small and
noisy (replicate/measurement variation), ~80-170 ingredients across 13 categories
with many rare one-off ingredients, percentages summing to 100%, plus standardised
process parameters (temperature, mixing speed, time).
**Method:** Generated by the Talos `deep-research` engine - 5 parallel Sonnet
sub-agents (Context7 -> official docs -> WebSearch -> cross-verify), synthesised
here. Confidence + source type tagged per finding; provenance gate at the end.
**Date:** 2026-06-11.

---

## 0. Executive summary - the architecture the evidence supports

The literature converges hard on a **two-stage "surrogate + optimiser"** pattern,
and our data regime (small, noisy, ~600 rows) sharpens almost every choice:

1. **Forward surrogate** (recipe -> properties): on small tabular data the reliable
   winners are **gradient-boosted trees (CatBoost/LightGBM/XGBoost)**, **Random
   Forest/ExtraTrees**, and crucially **TabPFN v2.5**, a tabular foundation model
   that is in its *sweet spot* at ~600 rows x <100 features and frequently beats
   *tuned* GBTs with zero tuning. Neural nets are unreliable below ~1000 rows.
   Keep an **ElasticNet** linear baseline as a sanity/interpretability anchor.
2. **Featurisation**: a **hybrid** scheme - individual `%` columns only for
   ingredients seen in >= ~5 recipes, with all rarer ones folded into their
   **13 category-mass** features - is exactly what the rare-ingredient evidence
   recommends (frequency-threshold collapse; avoid target-encoding rare levels;
   trees are scale-invariant so log-ratio transforms are optional). This directly
   implements the user's own insight.
3. **Honesty about noise**: compute a **noise ceiling** R2_max = 1 - sigma2_noise /
   sigma2_total from the replicate measurements, and report model R2 *relative to
   that ceiling*. Use **GroupKFold keyed on a recipe fingerprint** so duplicate /
   near-duplicate recipes can't leak between train and test (the classic cause of
   fake-high scores - and a likely reason a prior attempt looked off).
4. **Inverse design**: **scipy `differential_evolution`** over the surrogate, with a
   `LinearConstraint` for sum-to-100%, per-ingredient `bounds`, objective =
   **weighted normalised relative error** across the target properties; warm-start
   the population from k-NN nearest real recipes; multi-start + cluster for diverse
   candidates. Generative models (VAE/GAN) are **not** viable at 600 rows.
5. **Multi-target handling**: combine the (auto-selected top-5) targets with the
   weighted-normalised-error scalar objective, optionally upgraded to
   **Derringer-Suich desirability** for "above X / below Y / near X" goals, and
   optionally a **pymoo NSGA-II** Pareto front when the user wants to *see*
   trade-offs rather than one weighted recommendation.

The rest of this file is the evidence, grouped by the six research areas, then a
concrete mapping to the notebook build, a sources table, and the provenance gate.

## 1. Forward surrogate models for small, noisy tabular regression

**Tabular foundation model TabPFN v2.5 is the headline finding for our size.**
- "CPU usage is feasible only for small datasets with around 1000 samples or fewer";
  "TabPFN-3 supports up to 1,000,000 rows x 200 features ... or 1,000 rows x 20,000
  features." Our ~600 x <100 sits comfortably inside the CPU-feasible regime.
  [HIGH, official-repo] https://github.com/PriorLabs/TabPFN
- "default TabPFN-2.5 has a 100% win rate against default XGBoost on small to
  medium-sized datasets (<=10,000 data points)"; "85% win rate for regression".
  [HIGH, academic-paper] https://arxiv.org/abs/2511.08667
- Small-data active-learning surrogate benchmark (materials, the closest analogue
  to formulation): "TabPFN wins on 8 out of 10 datasets ... mean saving of 52% in
  extra evaluations relative to GP and 29.77% relative to RF"; "~5% MAE around 100
  training samples while tuned baselines lag." [HIGH, academic-paper]
  https://arxiv.org/abs/2603.12567
- Regression API (no scaling / one-hot needed):
  `from tabpfn import TabPFNRegressor; reg = TabPFNRegressor(); reg.fit(X,y);
  reg.predict(Xt)`. [HIGH, official-repo] https://github.com/PriorLabs/TabPFN
- Failure mode that does NOT apply to us: "On high-dimensional datasets, TabPFN v2
  fails to outperform even ... Logistic Regression" - only bites at very high
  feature counts; at 60-100 features we're safe. [HIGH, academic-paper]
  https://arxiv.org/html/2502.17361v1

**Gradient-boosted trees remain the dependable workhorse.**
- Comprehensive benchmark on <1000-row datasets (36 datasets): best avg ranks went
  to CatBoost (5.1) and H2O-GBM (5.6); RandomForest 6.1; XGBoost 6.6; MLP 6.3;
  ResNet 6.7. Trees and DL are close, but trees are more *reliable*. [HIGH,
  academic-paper] https://arxiv.org/html/2408.14817v1
- Small-data settings that matter: shallow trees (max_depth 3-6), low learning rate
  (0.01-0.1), L2 reg_lambda 1-10, raised min_child_weight/min_child_samples (5-20),
  100-500 estimators with early stopping. [MEDIUM, blog]
  https://www.bohrium.com/en/blog/tutorials/xgboost-vs-lightgbm/
- CatBoost: native high-cardinality categorical handling + built-in overfit
  detection - attractive if any ingredient identity is used as a category. [MEDIUM,
  search-snippet]

**Neural nets / GP / linear baselines.**
- "Only a subset of methods - gradient boosting ensembles, carefully tuned MLP
  variants, retrieval-based methods, and pretrained foundation models - achieve
  consistent and stable improvements." Untuned MLPs unreliable < ~1000 rows.
  [HIGH, academic-paper] https://arxiv.org/html/2407.00956v4
- GP is the canonical *Bayesian-optimisation* surrogate (analytic uncertainty) and
  is fine at <1000 points (O(n^3) beyond ~5000), but "GP underfits complex
  composition-property landscapes due to rigid kernel assumptions." Use GP only if
  doing a closed-loop BO; for pure accuracy TabPFN/CatBoost win. [HIGH,
  academic-paper] https://arxiv.org/abs/2603.12567 ; [MEDIUM]
  https://www.mdpi.com/2073-4360/18/8/902
- ElasticNet: fast, interpretable lower-bound. "Elastic Net ... especially with
  high-dimensional data and small samples." If a property is nearly as well
  predicted by ElasticNet as by trees, it is near-linear in formulation - useful
  domain knowledge. [MEDIUM, blog]
  https://towardsdatascience.com/the-choice-of-regularization-ridge-lasso-and-elastic-net-regression-fc696f697209/

**=> Forward-model plan:** benchmark ElasticNet, RandomForest, ExtraTrees,
HistGBR, XGBoost, LightGBM, and TabPFN (optional, behind try/except - pulls in
torch) per property, with leakage-safe CV (section 3). Expect TabPFN or CatBoost/
LightGBM to lead. Report all against the noise ceiling.

## 2. Ingredient / formulation featurisation

**Hybrid frequency-threshold scheme is the recommended representation.**
- Rare levels should be collapsed: high-cardinality features "follow a power-law
  ... practitioners can leverage this by grouping less frequent categories into a
  single 'Other' or 'Rare' category." [MEDIUM, blog] (apxml high-cardinality guide)
- scikit-learn `OneHotEncoder(min_frequency=..., max_categories=..., handle_unknown=
  'infrequent_if_exist')` implements exactly the "frequent get own column, rare fold
  into one bin" logic for identity features. [HIGH, vendor-doc]
  https://scikit-learn.org/dev/auto_examples/release_highlights/plot_release_highlights_1_1_0.html
- `feature-engine` formalises it as **RareLabelEncoder** (cardinality reduction
  below a frequency threshold). [HIGH, vendor-doc]
  https://feature-engine.trainindata.com/en/1.8.x/user_guide/encoding/index.html
- **Target-encoding rare ingredients is dangerous**: for an ingredient in 1-2
  recipes the encoded value ~ equals that recipe's target -> leakage/overfit.
  "Highly cardinal features can ... lead to overfitting in tree-based models."
  Use frequency threshold >= 5 before giving an ingredient its own column. [MEDIUM,
  academic-paper] https://www.cambridge.org/core/services/aop-cambridge-core/content/view/C910580D669A903DA6CC00AE6CDCB4DE/S0515036124000072a.pdf

**Category grouping vs individual - the user's "starches differ" caveat is real.**
- Grouping reduces dimensionality but "loses within-category signal" when two
  same-category ingredients have opposite functional effects. The hybrid resolves
  it: distinct common starches keep their own columns; obscure one-offs roll up to
  "Starch %". [MEDIUM, mixed sources incl. USPTO 10984145 "many possible
  combinations of ingredients are featurized into relatively few aggregated
  ingredient properties"] https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10984145

**Compositional (sum-to-100%) data - closure.**
- "Whenever your variables represent parts of a whole ... they must sum to a
  constant ... This constraint, called closure, causes ... spurious correlations."
  [HIGH, blog] https://metricgate.com/blogs/compositional-data-analysis-guide/
- Log-ratio transforms (CLR/ILR/ALR) fix closure for *linear* models/PCA; for
  **tree models they are largely unnecessary** (trees are scale-invariant) and add
  zero-handling overhead (most ingredient %s are 0; need epsilon ~0.001). "Tree
  ... models are scale-invariant and do not suffer from spurious correlations due
  to closure in the same way as linear models." Regression methods can be "affine
  equivariant ... the same predictions for every logratio transformation." [HIGH,
  academic-paper] https://jbds.isdsa.org/jbds/article/download/72/92/386 ; [MEDIUM]
  https://medium.com/@nextgendatascientist/a-guide-for-data-scientists-log-ratio-transformations-in-machine-learning-a2db44e2a455
- Classical **Scheffe mixture model** (drop the intercept because the x's are
  constrained) is the formal DoE framing for sum-to-1 designs. [HIGH, vendor-doc]
  https://online.stat.psu.edu/stat503/lesson/11/11.3

**Process variables join the model outside the simplex.**
- "Process variables are factors such as heat or time that do not form any portion
  of the mixture but whose levels ... could affect the blending properties."
  Mixture-process models add them as plain features and allow
  mixture x process interaction terms. [HIGH, vendor-doc]
  https://online.stat.psu.edu/stat503/lesson/11/11.3 ; [MEDIUM]
  https://arxiv.org/pdf/1509.04984

**Optional enrichment (future):** represent ingredients by physicochemical/
nutritional descriptor vectors (FoodData Central / FooDB) so even a 1-recipe
ingredient carries signal via similarity. Food-AI nets take "weighted ingredient
vectors as input." [HIGH, academic-paper] https://pmc.ncbi.nlm.nih.gov/articles/PMC12098880/

**=> Featurisation plan:** frequency split at N=5-8 -> individual `%` columns for
common ingredients + 13 category-mass columns (always present) + ingredient count
+ process summaries. Trees on raw proportions (no CLR). Keep an ablation toggle
(category-only vs hybrid vs full) to *measure* whether grouping helped rather than
assume - directly answering the user's uncertainty. Descriptor enrichment is a
documented upgrade path.

## 3. Noise ceiling + leakage-safe cross-validation (data validity)

**Noise ceiling - the single most important honesty metric here.**
- Formula: **R2_max = 1 - sigma2_noise / sigma2_total**, where sigma2_noise is the
  within-replicate (measurement) variance and sigma2_total the total response
  variance. Follows from the bias-variance decomposition (irreducible error).
  [HIGH, textbook] https://daviddalpiaz.github.io/r4sl/biasvariance-tradeoff.html
- Dedicated paper: "a theoretical upper bound for the coefficient of determination
  (R2) ... depends only on the noise associated with the response variable ... as
  well as its variance." [HIGH, academic-paper] https://arxiv.org/abs/1912.08141
- Estimation from replicates: per recipe i compute within-replicate variance s2_i;
  sigma2_noise = mean(s2_i); sigma2_total = var(all measurements); R2_max =
  1 - sigma2_noise/sigma2_total. Tooling precedent: the `noiseceiling` package
  "uses repeated observations to estimate the variance ... across those
  repetitions." [HIGH, software] https://github.com/lukassnoek/noiseceiling
- SNR duality: R2 = SNR/(1+SNR). If sigma2_noise >= sigma2_total/2 then R2_max <=
  0.5. [HIGH, vendor-doc] https://statproofbook.github.io/P/snr-rsq.html
- Repeatability metrics: **ICC** = sigma2_between/(sigma2_between+sigma2_within),
  "0 if grouping conveys no information ... 1 if all observations in a group are
  identical"; ICC > ~0.75 acceptable. **Gauge R&R** %GRR > 30% => measurement
  system inadequate. [HIGH, vendor-doc] https://en.wikipedia.org/wiki/Intraclass_correlation

**Aggregate replicates before modelling.**
- Take per-recipe **median** (robust to instrument-outlier replicates) or mean if
  clean; averaging k replicates cuts noise variance ~1/k, raising R2_max.
  Median-of-means is a theoretically sound robust estimator. [HIGH, academic-paper]
  https://arxiv.org/pdf/1711.10306

**Leakage from duplicate / near-duplicate recipes (the silent score-inflator).**
- "When duplicate rows exist, one duplicate may be in the training data while
  another is in the test set, causing increased performance that is not actually
  true." [HIGH, blog]
  https://towardsdatascience.com/what-is-data-leakage-and-how-can-it-be-avoided-in-machine-learning-eb435a27c3e3/
- Fix with **group-wise CV**, official scikit-learn guidance: "if we know that the
  generative process has a group structure (samples collected from different
  subjects, experiments, measurement devices), it is safer to use group-wise
  cross-validation." `GroupKFold` "ensures that the same group is not represented
  in both testing and training sets." [HIGH, vendor-doc]
  https://scikit-learn.org/stable/modules/cross_validation.html
- APIs: `GroupKFold`, `StratifiedGroupKFold`, `LeaveOneGroupOut`, all via
  `.split(X, y, groups=recipe_fingerprint)`. [HIGH, vendor-doc]
  https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.StratifiedGroupKFold.html
- "A large drop in score with GroupKFold usually means your original evaluation was
  leaking information." [HIGH, blog]
  https://ai.plainenglish.io/grouped-data-cross-validation-with-scikit-learn-groupshufflesplit-and-groupkfold-d43a46bfab99

**Stable estimates on ~600 rows; avoid LOO.**
- Official doc: "LOO often results in high variance as an estimator for the test
  error ... most authors and empirical evidence suggest that 5 or 10-fold cross
  validation should be preferred to LOO." Use **RepeatedKFold** (here:
  repeated GroupKFold) for stability. [HIGH, vendor-doc]
  https://scikit-learn.org/stable/modules/cross_validation.html ; LOO distributional
  bias [HIGH, academic-paper] https://arxiv.org/pdf/2406.01652

**=> Validity plan:** (1) compute R2_max + ICC per property from replicates;
(2) aggregate replicates by median per (trial, parameter, measurement-condition);
(3) build a recipe fingerprint (rounded ingredient vector hash) as the CV group;
(4) repeated GroupKFold (5-fold x several repeats) for all benchmarking;
(5) report R2 and R2 / R2_max so "0.45" reads as "good" when the ceiling is 0.50.

## 4. Inverse design / inverse formulation under mixture constraints

**Surrogate + Differential Evolution is the proven, scale-appropriate choice.**
- Closest precedent (food taste, only 70 recipes, 5 targets) - objective verbatim:
  **Pi = sum_j W_j * |T*_j,desired - T*_j| / |T*_j|** (weighted relative error).
  DE settings: strategy `best1bin`, popsize 15, mutation F in [0.5,1.0],
  recombination 0.8, maxiter 500; mixture constraint sum_i v_i = 1; per-ingredient
  bounds v_i^min <= v_i <= v_i^max. [HIGH, academic-paper]
  https://arxiv.org/html/2604.20206v1
- scipy API: `differential_evolution(func, bounds, strategy='best1bin', popsize=15,
  mutation=(0.5,1), recombination=0.7, constraints=..., polish=..., init=...)`;
  `constraints` accepts `LinearConstraint`/`NonlinearConstraint`;
  `updating='deferred'` required with `workers>1`; `init` can warm-start the
  population. [HIGH, vendor-doc]
  https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.differential_evolution.html

**Constraint handling on the simplex - three documented options.**
1. **LinearConstraint equality** (cleanest): `LinearConstraint(np.ones((1,n)),
   1.0, 1.0)` - scipy enforces sum-to-1 natively (`keep_feasible=True` available).
2. **Repair/projection**: after mutation, clip to bounds then rescale to sum 1
   ("handled through repair by projection"). [HIGH, peer-reviewed]
   https://peerj.com/articles/cs-2095/
3. **Softmax/Dirichlet reparam**: optimise z, use x = softmax(z) - always valid but
   distorts the geometry. [MEDIUM] (arXiv 2401.13171)
   Penalty terms (lambda*(sum-1)^2) are the weakest option.

**Warm start + diversity.**
- Seed the DE `init` population with **k-NN nearest real recipes** (query
  `sklearn.neighbors.NearestNeighbors` in normalised target-property space) - gives
  a realistic, sparse skeleton. Warm-starting "can reach comparable solutions in as
  few as 10% as many optimization steps." [MEDIUM] (arXiv 2412.13281; pattern
  inferred - no food-specific citation found).
- **Diverse candidates**: multi-start DE (10-20 seeds) + cluster the converged
  solutions (k-means) to return k distinct prototypes; or niching DE with archive.
  [HIGH, peer-reviewed 2025] https://link.springer.com/chapter/10.1007/978-981-96-7036-9_26

**Generative inverse design (VAE/GAN) - NOT at 600 rows.**
- CVAE inverse-design work itself calls a 1,503-point set "small" and still trains
  an MLP surrogate over it; VAEs typically need >1000 diverse samples to avoid
  latent collapse. "DE + surrogate is strongly preferred at this scale." [MEDIUM,
  academic-papers] https://arxiv.org/html/2510.05160 ;
  https://www.sciencedirect.com/science/article/pii/S0924224423001693

**Bayesian optimisation - only for closed-loop wet-lab.**
- BoFire/BoTorch support mixture (linear-equality) and NChooseK constraints and
  multi-objective acquisition (qNEHVI). Use BO if you will run *new* experiments in
  a loop; for in-silico inversion against a fixed fast surrogate, **DE is faster
  and simpler**. [HIGH, peer-reviewed] https://arxiv.org/html/2408.05040v1

**=> Inverse plan:** scipy `differential_evolution` over the per-target surrogates;
`LinearConstraint` sum-to-100% + per-ingredient `bounds` from observed ranges;
objective = weighted normalised relative error (section 5); restrict to a realistic
ingredient palette (warm-start from k-NN neighbours) for sparse, manufacturable
recipes; co-optimise the standardised process scalars (temp/time/speed); multi-
start + cluster for a best recipe + 2 alternatives; optional SLSQP `polish`.

## 5. Multi-objective handling across the 5 target properties

**Primary objective: weighted normalised relative error (scalarisation).**
- Same form as the taste precedent: **L = sum_j W_j * |y_pred_j - y_target_j| /
  |y_target_j|** - dimensionless, comparable across heterogeneous units, per-
  property weights. [HIGH, academic-paper] https://arxiv.org/html/2604.20206v1
- Weighted-sum caveat: "can only recover Pareto-optimal points on the convex hull";
  **Tchebycheff** scalarisation recovers non-convex Pareto regions. [HIGH,
  survey/journal] https://arxiv.org/pdf/2206.07438 ;
  https://link.springer.com/article/10.1007/s10898-023-01284-x

**Desirability functions (Derringer-Suich) - the chemometrics standard for "above
X / below Y / near X".**
- Individual desirabilities d_r in [0,1]: larger-is-better, smaller-is-better, and
  target-is-best (two-sided) piecewise forms with steepness s. Overall
  **D = (prod_r d_r)^(1/R)** (geometric mean) - "if any one model is undesirable
  (d_r = 0), the overall desirability is also unacceptable (D = 0)." [HIGH,
  tutorial faithfully reproducing Derringer-Suich 1980]
  https://sequential-parameter-optimization.github.io/Hyperparameter-Tuning-Cookbook/bart25a-desirability-latest.html
- "In range" goals act as soft gates (d=1 inside, 0 outside; excluded from the
  geometric-mean exponent). [HIGH, software-doc]
  https://www.statease.com/docs/v23.1/contents/optimization/desirability-details/
- Python food precedent (bread formulation: per-property desirabilities -> geometric
  mean -> scipy.optimize). [MEDIUM, tutorial]
  https://towardsdatascience.com/optimizing-multi-objective-problems-with-desirability-functions/

**Target normalisation.** Min-max `(Q-Qmin)/(Qmax-Qmin)` or divide-by-target so "no
single component dominates due to scale differences"; divide-by-target preferred for
physical properties with meaningful absolute values. [HIGH, journal]
https://link.springer.com/article/10.1007/s40747-017-0061-9

**True Pareto fronts (optional, for showing trade-offs).**
- **pymoo NSGA-II** (`n_obj=5`, `n_ieq_constr` for hard bounds via `out["G"]`,
  g<=0 convention); **NSGA-III** for many-objective via reference directions.
  Present a front of candidate recipes; highlight the one closest to default
  weights, table the rest. [HIGH, official-docs]
  https://github.com/anyoptimization/pymoo

**=> Objective plan:** default = weighted normalised relative error across the
auto-selected top-5 properties (equal weights, user-adjustable). Upgrade path:
Derringer-Suich desirability so the user can say "hardness near X, moisture below
Y, melt above Z"; optional pymoo NSGA-II Pareto mode to surface trade-offs as
alternative recipes.

## 6. Concrete build mapping (what goes in the notebook)

| Stage | Decision (evidence-backed) | Section |
|---|---|---|
| Data prep | median-aggregate replicates per (trial, parameter, texture-type); recipe fingerprint = group key | s3 |
| Noise floor | R2_max = 1 - sigma2_noise/sigma2_total + ICC per property; report ratio R2/R2_max | s3 |
| Features | hybrid: individual % for ingredients in >=5 recipes + 13 category sums + count + process summaries; raw proportions for trees (no CLR); ablation toggle | s2 |
| Forward CV | repeated GroupKFold(5) on fingerprint; compare ElasticNet, RF, ExtraTrees, HistGBR, XGBoost, LightGBM, (TabPFN optional) | s1, s3 |
| Top-5 select | rank properties by CV R2 (and R2/R2_max); auto-pick top 5, overridable cell | s1, s3 |
| Interpretability | SHAP / impurity importances on the chosen targets | s1 |
| Inverse engine | scipy differential_evolution, LinearConstraint sum=100%, per-ingredient bounds, weighted normalised relative-error objective, k-NN warm start, realistic palette, multi-start+cluster, co-optimise temp/time/speed | s4, s5 |
| Output | best recipe + 2 alternatives; predicted-vs-target table; nearest real recipe for sanity; optional Derringer-Suich / pymoo Pareto | s4, s5 |

**Honest expectation:** with ~600 noisy recipes some properties (likely texture
hardness, melting, moisture/fat) will predict well and others will sit near their
noise floor. The predictability ranking is itself a key deliverable and drives the
choice of the 5 design inputs.
